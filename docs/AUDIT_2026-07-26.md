## 1 · Security & Authorization

Scoped to modules that postdate the 2026-07-17 audit (`vault`, `consent`, `portal`, `checkout`, `payment-gateway`, `webhooks`, `entitlements`, `ai-vision`, `accidents`, `agency-staff`) plus a fresh IDOR sweep of everything else.

**Solid, verified clean:** `vault` (tenant-scoped, filenames sanitized, defense-in-depth MIME/size checks, 300s-expiry signed URLs), `consent` (grant invariant re-verified on every read, including the download path), `portal` (every handler keyed on JWT `user.id`, never a param), `checkout`/`payment-gateway` (money-of-record is always the server Decimal, Stripe signature verification is real), the webhooks outbound SSRF guard (DNS-rebinding fix confirmed wired), `agency-staff` (anti-escalation + last-owner/last-staff-manager lockouts), `saas-admin` (class-level `ROOT_ADMIN` gate). No hardcoded secret fallbacks or secret/token logging found anywhere in `backend/src`.

- **[M] Mock payment settlement has no production fail-safe** — `backend/src/payment-gateway/payment-gateway.service.ts:30` defaults to the `MOCK` gateway whenever `PAYMENT_PROVIDER` is unset/unrecognized. `providers/mock.gateway.ts:40-56` accepts an unsigned `{providerRef, status:'PAID'}` body as proof of payment, and the `providerRef` is echoed back to the customer in their own redirect URL — so a customer could `POST /payments/webhooks/mock` directly and mark their own invoice paid for free. `settleCheckout`'s idempotency guard only blocks *double*-settlement, not a *forged* one. Nothing refuses `MOCK` when `NODE_ENV=production`. **Fix:** hard-refuse the mock gateway outside dev/test, or require an explicit opt-in flag.
- **[M] `GET /agency/billing` has no capability gate** — `backend/src/entitlements/entitlements.controller.ts:20-24` is guarded by `AuthGuard` alone. Any authenticated staff member — including a 14-capability AGENT — can read the agency's subscription plan, usage meters, and full `PlatformInvoice` history. Every comparable agency-scoped read elsewhere requires `@RequireCapabilities`; this is the one exception. **Fix:** gate with `finance.view` or a new `billing.view` capability.
- **[M] `POST /ai-vision/analyze` has no upload limits** — `backend/src/ai-vision/ai-vision.controller.ts:26` uses a bare `FileInterceptor('image')`, no `limits.fileSize`, no `fileFilter` — unlike `vault.controller.ts`/`portal.controller.ts` which both cap and whitelist. Any user with `fleet.view` can send an arbitrarily large multipart body that multer buffers fully into memory. Low urgency today since the endpoint's analysis is mocked, but the unbounded buffering happens before that. **Fix:** add the same limits pattern used in vault/portal.

## 2 · Data & Money Correctness

**Phase 2 backlog re-check** (all six items listed ⬜ open as of 2026-07-17 in `docs/AUDIT_BACKLOG.md`):

|---|---|

| Seeds destructive/unscoped, missing `updatedAt` | **PARTIAL** — `updatedAt` added to Payment/RefusalLog; `seed.js` is still fully destructive with **no `NODE_ENV` guard** (documented, intentional follow-up — see #21) |

**New findings:**

- **[H] Concurrent REFUND verification can push a refund past net verified income** — `backend/src/payments/payments.service.ts:158-184`. The affordability check (`netVerifiedIncomeCents`) reads via `this.prisma` *before and outside* the `$transaction` that flips the payment to VERIFIED; the write inside the transaction has no compound guard re-validating the check. Two concurrent verifies of two separate PENDING refunds (double-click, retry) can each read the same pre-verify net-income figure, both pass the check, both commit — refunding more than was ever actually paid in. This is exactly the check-then-act-outside-`tx` anti-pattern CLAUDE.md §5.5 exists to prevent, and it directly violates the explicit invariant from Phase 3 ("a refund can never exceed net verified income"). **Fix:** move the affordability read inside the `tx` using the transaction client, or re-validate with a compound `where` on the update.
- **[M] Concurrent deposit CLAIM can double-charge a damage claim** — `backend/src/bookings/bookings.service.ts:640-707`. Same shape: `depositStatus !== 'HELD'` is checked once against a pre-fetched object read via `this.prisma`, then `tx.booking.update` has no `depositStatus: 'HELD'` guard in its `where`. Two concurrent CLAIM calls on the same booking would each create their own `claimExtra` INCOME payment. Lower severity than the refund case (staff-only, single-actor, rarer), same mechanism. **Fix:** same as above — compound `where` guard or move the check inside `tx`.
- **[L] HOLD/RETURN deposit actions non-transactional** — `bookings.service.ts:588-604` and `:618-627`, no `$transaction`, no compound `where`. No money write in either branch, so worst case is a duplicate AuditLog entry, not a financial bug. Noted for consistency with the CLAIM/verify fix above.
- **[L] `seed.js` still fully destructive, no `NODE_ENV` guard** — 13 `deleteMany()` calls with nothing stopping it from being run against a wrongly-pointed `DATABASE_URL`. Matches CLAUDE.md's own documented Phase-2 follow-up.

**Migrations:** all 13 reviewed; no unsafe `NOT NULL ADD COLUMN` without backfill+default. The two newest (`vault_file`, `vault_entity_linking`) only add nullable columns — safe.

## 3 · Performance & Reliability

**Backlog re-check:** two of the three items marked open on 2026-07-17 are actually **fixed**:

- "~13 sequential awaited queries" — largely a non-issue on inspection; the sequential `await`s found are genuinely dependent check-then-act sequences, not accidental serialization. One cosmetic `Promise.all` opportunity at `bookings.service.ts:41-42` (**L**).
- Unbounded customers/cars/payments lists — **FIXED**: `customers.service.ts:78` (`take: 500`), `cars.service.ts:81` (`take: 500`), `payments.service.ts:38,62` (`take: 100`/`200`).
- PDF engine Puppeteer risk — **FIXED**: HTML-escaping (`esc()`) applied to every user-controlled field; `try/finally` now closes the browser unconditionally. Still won't run on Vercel as-is, but that's the already-known Phase 9 deploy-target decision, not a bug.

**New findings:**

- **[M] Dead, unscoped `findExpiringSoon()`** — `backend/src/documents/documents.service.ts:162`. Zero callers anywhere in the repo, but it also has no `agencyId` filter (cross-tenant — returns every agency's expiring documents) and no `take` (full-table scan as `CarDocument` grows). Harmless while unused, but a landmine the moment someone wires it to an expiry-notification cron without independently noticing both bugs. **Fix:** scope + cap it now, or delete it.
- **[L] `cars.service.ts` caps at 500 with no truncation signal** — unlike `customers.service.ts` (which exposes a paginated envelope), a fleet over 500 cars silently truncates in the UI with no `totalCount` returned.
- **[L] `portal.service.ts` `bookings()`/`notifications()` have no `take`** — small blast radius (single renter's own rows) but `notifications` in particular can grow unbounded over years with no cap or archive path.
- **[L] Cron jobs have no single-instance guard** — 4 `@Cron` jobs (consent expiry sweep, 3x automations) confirmed with no leader-election/DB-advisory-lock/env-flag. Fine on one instance; will double-fire (duplicate charges/notifications) the moment the backend runs multi-replica. Matches the already-known Phase 9 item — confirmed still open, correctly scoped there.
- **[L] `AuditLog` has no `createdAt` index** for the platform-ordered read — already flagged in-code as a deferred, low-volume tradeoff. Confirmed still open.

## 4 · Frontend (incl. uncommitted Vault UI)

### Uncommitted files (highest priority — never reviewed before now)

- **[H] `VaultAccessPanel.tsx:70-105` — no identity cross-check on the QR-resolved renter.** The panel binds an arbitrary agency-supplied `renterUserId` to a `Customer.id` purely via `localStorage` (`fider:vault-consent-renter:${customerId}`), with no server-side or UI verification that the QR-resolved renter is actually the same person as the Customer record being viewed — the file's own comment admits there's no schema link. If staff scans/pastes the wrong renter's code (easy at a busy desk, two customers with similar names), the panel silently shows a *different renter's* private ID/license/passport documents under an unrelated customer's profile — reproducible via the new e2e test itself (`customer-vault-access.e2e.ts:118-123`). Not a server-side authz bypass (the consent grant is still real), but a real PII-misattribution risk. **Fix:** surface the resolved renter's name/photo next to "Digital vault access" so staff can visually confirm the match before viewing documents.
- **[M] New Vault UI is entirely hardcoded English** — `VaultAccessPanel.tsx`, `UploadDocumentModal.tsx`, and the new additions to `portal/page.tsx:159-179` never route through next-intl `t()`, even though the surrounding page already does (`t('documents')` sits right next to the new hardcoded-English Upload button). Root cause: `ToastContext.tsx:35-60` only translates toast titles that are hand-added to a `TOAST_KEYS` map — none of the new titles are in it, and toast *messages* never translate regardless. AR/FR users get an all-English experience on the entire new feature, contradicting the Phase 7 next-intl work.
- File upload validation, error/loading/empty states, `dangerouslySetInnerHTML`, shared-Modal reuse — all checked, **no issues**.

### Design-system / doc-accuracy

- **[H] `docs`/`CLAUDE.md`'s Phase 12 claim "`font-black` is 0 files app-wide" is false.** `grep -rn "font-black"` finds 8 live files, including two shared, everywhere-used components: **`components/ui/Modal.tsx:123`** (every dialog title in the app, including the brand-new `UploadDocumentModal`) and **`components/ui/EmptyState.tsx:33`** (used by `VaultAccessPanel`'s own "No active consent" state) — both still on `text-white uppercase font-black`, not the Fider Lux tokens. Also present in `Combobox.tsx` and `CommandPalette.tsx`. This is visible on essentially every page via the shared chrome. **Fix:** migrate `Modal.tsx` and `EmptyState.tsx` to the design tokens; update the Phase 12 claim in `CLAUDE.md`/`AUDIT_BACKLOG.md` once done.
- **[M] `components/ui/Combobox.tsx` entirely unmigrated** — hardcoded `bg-white/5`, `border-white/10`, `text-white`, inline `rgba(9,12,20,0.98)`, not a single Fider Lux token. Used in booking/customer-assignment forms.
- The CLAUDE.md-flagged "`(renter)/portal/types.ts` has raw colors" item is **stale** — current file (187 lines, fully read) has zero raw-white/hex hits; already fixed.

### Accessibility (Phase 7 items marked "not audited" on 2026-07-17)

## 6 · Dependencies & DevOps

- **[M] 8 backend npm vulnerabilities, 6 High** — `@nestjs/platform-express` (→ vulnerable `multer` DoS via nested fields / incomplete upload cleanup), `axios`, `form-data` (CRLF injection), `js-yaml` (quadratic DoS), `qs` (moderate), `ws` (memory disclosure + exhaustion DoS). All have fixes available via `npm audit fix` — worth running and re-testing.
- **[M] 17 frontend npm vulnerabilities, 8+ High** — most notably `next` itself (16.2.4 → fix 16.2.12, a **non-major patch bump**, low risk to apply) covering a long list of advisories (DoS, middleware bypass, cache poisoning, XSS, SSRF in Server Actions/rewrites). `sharp` is a transitive dep of `next`'s image optimizer and resolves with the same bump. `hono`/`@modelcontextprotocol/sdk`/`shadcn`-related entries are transitive to the `shadcn` CLI tool, not runtime app code — lower real-world exposure but still worth a `npm audit fix` pass.
- **[M] `.env.example` drift** — `backend/.env.example` is missing `PAYMENT_PROVIDER`, `PUBLIC_APP_URL`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `DAMAGE_AUTO_CHARGE_PLACEHOLDER_AMOUNT` (all real, referenced in code). There is **no `frontend/.env.example`** at all despite `NEXT_PUBLIC_API_URL` being required, and no root `.env.example` for `DB_USER`/`DB_PASSWORD`/`DB_NAME`. A fresh setup following the example files alone would silently miss required config. **Fix:** regenerate all three example files from an env-var grep.
- **[L] Deploy items — confirmed still open, matches existing Phase 9 backlog, no new action needed beyond what's already tracked:** `backend/Dockerfile` has no `prisma migrate deploy` step before `CMD` (a fresh container boots against unmigrated schema); `docker-compose.yml` sets `NEXT_PUBLIC_API_URL` as a runtime `environment:` var, but Next.js inlines `NEXT_PUBLIC_*` at **build** time, so the value baked into the frontend image's build is whatever it was during `docker build`, not whatever compose sets at `docker run`; neither backend nor frontend container defines a healthcheck (only `db` does).
